## Границы приложения

Текущая рабочая папка — существующая папка материалов; репозиторий целиком не клонировался и не дублировался. Создан только MasterTime. Это локальная рабочая подпапка, еще не Git-checkout. Изменений в GitHub, main, корневой конфигурации и других проектах нет.

- `index.html`, `src/styles.css`, `src/app.mjs`: статический интерфейс, совместимый с размещением /MasterTime/. По умолчанию игровой вход #game/#play, остальные экраны — инструменты.
- `src/game.mjs`, `src/game-view.mjs`, `data/game-scenarios.mjs`: состояния первого игрового дня, программные последствия, исходные события и представление.
- `tools/build.mjs` → `assets/app.js`: производный скрипт без зависимостей, позволяющий file:// открытие игры и каталога. Исходные модули отдельно тестируются.
- `src/domain.mjs`: чистые календарные вычисления, интервалы, прогресс, однократные награды, снимки глав.
- `data/`: импортированные карточки и происхождение.
- `tools/`: повторяемый импорт и браузерная проверка.
- `tests/`: автоматические проверки; `docs/`: источники, перенос, расчеты, архитектура.
- `server/`: зарезервировано для отдельного серверного этапа. Сейчас серверного кода и базы нет.

## План серверной реализации

Выбранное направление — отдельный Worker и отдельная D1 `MASTER_TIME_DB`, чтобы не использовать MAMA_DB и не менять другие приложения. Конкретное размещение API и привязка домена требуют проверки доступа Cloudflare. До интеграции не добавлять фиктивные идентификаторы базы. Сначала отдельное тестовое окружение; затем проверенное включение API на согласованном поддомене или изолированном маршруте.

Сущности: users, identities, sessions, access_grants, profiles, tasks, goals, vacations, months, habits, habit_checks, card_runs, favorites, decisions, game_sessions, reward_ledger, achievements, chapter_revisions, notification_preferences, notification_outbox, activity_events, audit_events, mutation_receipts. Во всех личных таблицах user_id; выборки только с владельцем из серверной сессии, а не из тела запроса. Дневники не включать в административную статистику. Временные метки — UTC, календарные периоды — локальная дата и IANA zone.

API: `/auth/telegram`, `/auth/web`, `/access`, `/profile`, `/tasks`, `/months`, `/habits`, `/cards/runs`, `/decisions`, `/chapters`, `/exports`, `/notifications`, `/me/export`, `/me/delete`, `/admin/stats`, `/admin/access-code`. Каждый изменяющий запрос получает mutation_id; уникальность по (user_id, mutation_id) предотвращает повторное начисление/сохранение. Revision/If-Match обнаруживают конфликты двух устройств. Офлайн-очередь в IndexedDB; удаление — отдельные tombstones. Конфликт личных текстов не разрешать молча: сохранять обе версии.

Telegram initData проверять на сервере по официальному алгоритму HMAC, auth_date с коротким сроком действия, постоянным временем сравнения, строгим разбором полей и защитой повторного обмена. Никогда не доверять initDataUnsafe для выдачи доступа. Выдать случайный серверный session token, хранить только его хеш, cookie Secure/HttpOnly/SameSite с ограниченным сроком. Защищать изменяющие запросы проверкой Origin и CSRF. Внешний веб-вход: WebAuthn/passkey или проверенный провайдер; решение и настройка еще нужны, не делать небезопасный вход по Telegram ID.

Код доступа: только серверный проверочный хеш с солью, секрет через защищенные настройки среды, ограничение попыток по учетной записи и IP, постепенная задержка. Смена администратором, audit без значения кода. Users — только название; роль по серверному allowlist проверенных Telegram ID. Любой endpoint admin требует повторной серверной проверки роли.

Уведомления: добровольное согласие с датой и версией, IANA zone, выбранные часы/дни/типы, отписка. Cron выбирает due записи, outbox с уникальным ключом пользователя/типа/локальной даты/времени; повторные попытки с задержкой, обработка Telegram 429/403, без отправки при отозванном согласии. При повторяющемся осеннем часе — одна доставка, при пропущенном весеннем — ближайшее доступное время. Точные правила показать в настройках.

Секреты: BOT_TOKEN, WEBHOOK_SECRET, SESSION_PEPPER, ACCESS_CODE_HASH и настройки роли только серверу. .env и .dev.vars игнорируются. Логи без initData, токенов и личных записей. CSP, строгие CORS origin, лимит размера JSON, валидация каждой сущности, подготовленные SQL-запросы и тесты изоляции пользователей обязательны перед публикацией.

Экспорт и удаление данных, резервные копии, срок хранения, восстановление из копии, политика приватности и сведения об обработчике нужны до сбора реальных аккаунтов. Подготовка архитектуры не является подтверждением соответствия GDPR.
